# Product research and suggestion engine

The [master audit baseline](master-audit-rules.md) takes precedence: reliable direct
Customer Request/FS matches pass without catalogue membership or AI. Research is
for unresolved differences, and source-only confirmations do not register products.

Implemented for General Auditor in the website and extension. Vaccine allocation,
Blueprint balances, deductions, facility/orderer matching and quantity exceptions
continue through their existing engines. No additional audit fields are mandatory.

## Behavior

1. Reliable direct source comparison, existing catalogue/approved aliases and
   compatible deterministic normalization resolve identities without research calls.
   Existing resolver caches remain.
2. Candidate retrieval includes approved aliases and close spelling. Ingredient,
   strength, presentation and device conflicts exclude unsafe suggested equivalents.
3. The existing batch Gemini path handles overlapping catalogue terminology. Unknown
   terms with no overlapping catalogue entries also get research: possible generic
   names are resolved against the catalogue, never accepted as new IDs or approvals.
4. Unresolved products show bounded candidates or specific clarification/new-entry
   steps. HIGH/MEDIUM/LOW describe evidence categories, never calibrated probabilities.
   Every model suggestion still requires explicit CCA verification.
5. Confirm, Reject and Search Again operate on the same audit. Search and rejection
   preserve comparison findings. Rejected choices remain excluded on Search Again.
6. Confirm atomically saves the verified alias, alias history and updated audit in
   Firestore. It retains the original request in the audit, links alias history to
   auditId/originalProductText, and records actor/time/fingerprint. Only the chosen
   product identity is reconciled; quantities and other identity discrepancies remain.
7. The existing Alias Dictionary lets catalogue administrators deactivate/correct
   mistaken approvals. Such aliases are excluded from future approved resolution.

## Configuration before deployment

All settings are server-side. Existing GEMINI_API_KEY is reused; never place it in
Vite variables, extension config or downloaded packages. No new dependency is needed.

| Variable | Default | Meaning |
| --- | --- | --- |
| PRODUCT_RESEARCH_MODEL | gemini-2.5-flash-lite | Terminology/candidate research model |
| PRODUCT_RESEARCH_TIMEOUT_MS | 3500 | Research request budget, clamped 100–10000 ms and bounded by the remaining audit budget |
| PRODUCT_RESEARCH_GOOGLE_SEARCH | false | Explicit opt-in to optional public grounding |
| PRODUCT_RESEARCH_SEARCH_MODEL | gemini-2.5-flash | Model supporting Google Search grounding |

One SDK attempt per stage; no automatic rate-limit retry. Existing Gemini shared
cooldown prevents repeated 429 calls. Successful analysis is cached for two minutes,
failures briefly, with catalogue content/revision and scope in the key. Search Again
explicitly bypasses the success cache; it does not bypass quota cooldown.
Public grounding results are also cached by the generated public query and model.

Normal research consumes the configured model's Gemini tokens under the existing
account. Enabling Google Search may add provider charges and requires a supported
model/account/quota. Review current provider pricing before enabling it:
https://ai.google.dev/gemini-api/docs/pricing
https://ai.google.dev/gemini-api/docs/google-search
No billing plan or production environment setting has been changed by implementation.

## Public search and sources

A separate grounding call receives only public medical terms selected from the
bundled medical terminology file. It never receives original messages, customer
names, contacts, order IDs, facility names, or arbitrary editable catalogue labels.
If no safe public medical term is available, it does not search: clarification or
human review is the next step. Thus web grounding does not promise to look up every
unfamiliar local brand or abbreviation.

Only actual provider grounding metadata with issued search queries and supported
HTTPS citation chunks is rendered. JSON/text URLs generated by the model are ignored.
No sources means no claim of a successful grounded search. References are research
evidence, not proof that the chosen catalogue item is equivalent. Provider search
suggestions are displayed in an isolated, script-disabled sandboxed iframe.

### Explicit product decisions (2026-11-04)

The website chooser now asks whether the source descriptions identify the same
product or a discrepancy. Select a candidate and verify its attributes before
choosing **Same product — Confirm & Resume**. **Different products — Mark
discrepancy** records the CCA's decision even when no supported candidate exists.
**Reject this suggestion** removes only a candidate; it does not approve a match
or decide the entire audit. Search Again remains available. All actions reuse the
existing saved-audit endpoints, ownership checks and decision history. Quantity
and unrelated identity findings remain independent. No new catalogue entries,
AI configuration or extension installation is required for this website change.

### Known catalogue entries with different IDs (2026-11-04)

The Akokoaso order exposed a gap: both `Folic Acid` and `Folic acid 5mg Tablet`
were recognised catalogue entries with different IDs. The identity comparison
remained unresolved, but the suggestion builder only considered unknown or
ambiguous names, leaving the CCA without a product choice.

Website comparisons now offer compatible same-ingredient FS entries as local,
audit-specific choices even when both names already have catalogue IDs. Approval
uses the existing source-product confirmation path and never redirects the
generic catalogue entry or learns a strength-specific alias globally. Explicit
clinical conflicts, rejected mappings, different ingredients and entries already
accounted for by another requested product are excluded. Final quantity checks,
stockouts and order-limit approval remain independent.

`server/generalKnownProductChoices.test.ts` covers the supplied three-product
order, same-audit confirmation, approved and rejected order limits, clinical
conflicts, rejected aliases and already-matched products. An isolated run against
the read-only production catalogue snapshot confirms D5% as out of stock, Ringer's
lactate as matched and Folic acid as cleared only after identity confirmation and
the approved order limit. No operational audit or catalogue data was written.
Validation: 67 focused tests passed; full local release checks passed with 1,936
tests passed, zero failed and one optional emulator test skipped (1,937 total).
The final build and TypeScript checks also passed after the candidate-accounting

### Concise, relevant FS candidates in the General Auditor (2026-11-04)

The website General Auditor no longer renders the broad `fulfillmentValue`
fallback (which may contain every FS product) inside a product suggestion. It
intersects supported suggestion options with actual FS product evidence, using
source wording or the existing canonical product ID, and displays the specific
FS wording. Alternatives absent from FS are not offered as FS matches. Multiple
supported FS candidates remain selectable. Decision IDs and backend actions are
unchanged; quantity comparisons, CCA verification and order-limit approvals keep
their existing behavior. Explanations and references are collapsed under
Suggestion details. This presentation change does not modify Vaccine Checker,
Blueprint, extension, catalogue data or shared audit validation.

Affected implementation: `src/components/GeneralCatalogueSuggestions.tsx`,
`src/components/GeneralInventory.tsx`, and
`src/utils/generalFsProductSuggestions.ts`. Regression tests cover the original
full-confirmation fallback, unrelated entries, multiple relevant FS candidates,
catalogue-ID display mapping, unchanged decision IDs and no-candidate handling.
A headless Chrome interaction check passed for the concise Folic acid card and
its confirm/discrepancy actions.

### Source-bound suggestion data (2026-11-04)

The source trace is: `App.tsx` sends the two original inputs to `/api/verify`;
the General Auditor branch in `server.ts` calls `runGeneralProductNameAudit`;
the existing customer and FS projections/extractors parse separate product
entries before catalogue matching. The response passes through
`completeGeneralAuditRun`, then `GeneralInventory` and
`GeneralCatalogueSuggestions` render it.

Previously the final response builder replaced each group's FS value with the
entire parsed FS product list. Background product research also retained that
broad value. The shared General Auditor `scopeGeneralFsSuggestion` now binds
each group's candidates, customer value and FS value to actual parsed source
entries before the API response is produced or a research update is saved.
Known unrelated catalogue families, conflicting stated attributes, absent FS
entries and rejected choices are excluded. Uncertain AI proposals remain
unapproved and require the existing CCA decision. Candidate explanations are
brief; relevant research terminology is retained without unrelated leads.

Search Again first reuses local source comparisons, then scopes any research
result through the same function. An approved request alias can use its verified
catalogue ingredient context to find a presentation. For a confirmed source pair,
audit-specific canonical evidence follows the selected FS identity; original
names and confirmation history remain intact and catalogue IDs are not rewritten.
Quantity validation, order-limit decisions and the final audit gate still run.
Vaccine Checker, allocations and Blueprint are outside this change.

`server/generalFsSuggestionFlow.test.ts` exercises the production General
Auditor engine, JSON response, real app completion adapter and review component
for bullets, numbered products, Unicode bullets and inline lists. It covers
multiple requests, relevant aliases, quantity mismatches, no counterpart,
multiple presentations, CCA confirmation and Search Again. It makes no production
audit, catalogue, allocation or AI writes.
Validation: 1,969 tests passed, zero failed and one optional emulator test skipped
