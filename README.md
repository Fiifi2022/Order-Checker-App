# OrderCheck

## Run

Use **Node.js 22 or newer** (required by Firebase Admin 14). With nvm, run `nvm use` to select the version in `.nvmrc`. Run `npm install`, then `npm run dev`. Use `npm run build` and `npm start` for production.

## Authentication setup

The app uses Firebase email/password and Google sign-in with server-verified ID tokens. Only accounts with an assigned team role can access the portal. Sessions persist through Firebase Auth; signing out removes the portal and its local state.

1. In the Firebase project from `firebase-applet-config.json`, enable **Authentication → Sign-in method → Email/Password** and **Google**. Add your application hostname (and `localhost` for development) to **Authentication → Settings → Authorized domains**.
2. Provide Application Default Credentials to the server, for example with `GOOGLE_APPLICATION_CREDENTIALS` pointing to a service account file outside the repository. Grant the service account Firestore access and Firebase Authentication access needed to check revoked tokens. Never put server credentials in `VITE_` variables or commit them.
3. Set `AUTH_BOOTSTRAP_ADMIN_EMAIL` to the verified Google email of your initial administrator. This grants access only when no stored role exists for that email. The role database must be reachable; errors fail closed. The bootstrap administrator can use either a verified email/password account or Google.
4. Sign in as that administrator and use **Team Roles** to assign roles by email. Save a persistent administrator role for your own email before removing the bootstrap environment variable. Roles are checked on each API request, so deleting a role removes access immediately.
5. Deploy `firestore.rules` to the configured Firestore database. These rules deny direct client access; all persistence uses the server Admin SDK. Existing permissive rules must be replaced to prevent bypassing API authentication.

Administrators manage team roles and blueprints. Warehouse members (including legacy DCO accounts) and Compliance Auditors have full blueprint administration: upload, edit, synchronize, reset, and delete blueprints, districts, cycles, facilities, and quotas. Warehouse members also manage stock and adjustments. CCA members run audits and confirmations. Compliance Auditors review records and run verification. A person can hold multiple roles; their permissions are combined. In Team Roles, use **Edit roles** and select all applicable roles. Existing single-role accounts remain supported. Identity switching is disabled, and writes use the authenticated actor.

`GET /api/health` remains public. Other API endpoints require `Authorization: Bearer <Firebase ID token>`, including browser extension requests. The extension signs in with Firebase email/password, refreshes ID tokens, and sends authenticated audits to the selected backend. Accounts must have verified email and an assigned role. Google-only users can ask an administrator for a password reset link to set a password on the same account.

## Sign-up and approval

Users can choose **Sign up** and enter their full name, position, Nest, email, and password. Passwords stay with Firebase Authentication; the application stores only name, position, Nest, and account identity in `user_profiles`. Email/password accounts receive a verification link. If profile saving or email delivery fails, users can complete their profile or resend verification while signed in.

New users see a pending-access screen until their email is verified and a role is assigned. Administrators open **Team Roles → Pending sign-ups → Review access**, choose the appropriate role and district, and save. A stated position does not grant an access role. Users can click **Check verification and access** after verification and approval. Google accounts without assigned access can also complete a profile.

Firebase’s [email/password authentication](https://firebase.google.com/docs/auth/web/password-auth) and [email verification](https://firebase.google.com/docs/auth/web/manage-users) documentation cover provider setup and email templates.

## Administrator account support

Open **Administration → Signed-up accounts** to view Firebase accounts, including users who have not completed their profiles. The view shows name, email, position, Nest, assigned role, email verification, disabled status, sign-up date, and last sign-in. Lists load 100 accounts per page; use **Load more accounts** to browse further.

Administrators can edit name, position, and Nest, assign or update roles, enable or disable accounts, revoke sessions, and set a new password for email/password accounts. Password changes revoke existing sessions. Administrators cannot disable their own account. Google passwords must be changed through Google.

Password reset and email verification links can be generated and copied for private delivery to the account holder. Generating a link does not send an email. Passwords and links are excluded from account action logs; action metadata is stored in `account_admin_logs`. Recovery responses are not cached. Firebase credential hashes are never included in account list responses.

The server service account needs Firebase Authentication user-management permissions (for example, the Firebase Authentication Admin IAM role) and Firestore access. Profile edits update Firestore and the Firebase display name; if a step fails, reload the details before retrying. These operations use Firebase’s [Admin user management](https://firebase.google.com/docs/auth/admin/manage-users) and [recovery link APIs](https://firebase.google.com/docs/auth/admin/email-action-links).

### Audit speed and AI fallback

Audits use saved aliases, facility references and existing validation rules first. Gemini runs only for unresolved interpretation, with one attempt and no automatic model retries. Failed interpretation preserves available findings and marks unresolved information for manual review. Confirmed identifier mismatches remain discrepancies.

Three seconds is a progress target. After three seconds the portal displays “Your audit is taking slightly longer than expected. Please wait while we complete the verification.” The default hard deadline is **20 seconds in the browser/companion** and **18 seconds on the server**. Optional AI has a **4-second** limit within that server deadline. Hard timeouts preserve the input fields, discard late results and allow retry. Cancellation propagates to supported fetch/Gemini operations. Firebase calls already in progress cannot always be cancelled; later verification steps stop. Allocation confirmation/deduction transactions retain their existing behavior and are not interrupted by these verification deadlines.

Configure `AUDIT_HARD_TIMEOUT_MS` on the server (4–60 seconds), `AUDIT_AI_TIMEOUT_MS` (100–15,000 ms), and `VITE_AUDIT_HARD_TIMEOUT_MS` when building the frontend (4–60 seconds). Keep the browser timeout above the server timeout to allow response transit. The companion defaults to 20 seconds and accepts `auditTimeoutMs` in its existing extension configuration. Invalid settings fall back to the defaults. Screenshot transcription and explicitly requested alias suggestions remain separate operations.

The server reads the current product catalog once per audit and returns that same catalog to the portal for reconciliation. Catalog revision checks remain supported for existing clients. Managed facility removals are read fresh; optional Blueprint identity enrichment runs alongside that read with a 1.2-second limit. History logging waits at most 200 ms and reports failures or delayed persistence. No stock, allocation or audit-result cache is introduced. Normalized reference vocabulary is cached with edit detection; AI extraction caches are scoped to the authenticated account and vocabulary version.

Set `AUDIT_PERFORMANCE_LOG=true` to emit numeric stage durations and counts for authentication, catalog reading/application, facility-reference reading, facility/orderer identification, product extraction/normalization, quantity verification, optional Gemini interpretation, final validation, history wait and API response/total time. Timings overlap where stages are nested or concurrent; do not add them together. Logs exclude order text, names, products, credentials and customer identifiers. Existing General Auditor debug hooks also exclude payload content. Diagnostics are off by default.

### Central General Auditor product matching

The original false Extra Product failure came from classifying normalized-name groups as missing/extra before checking structured clinical identity. A missing unit (`injection artesunate 120`), spelling error or partially specified formulation produced a different key, and the old missing-form review only handled a narrow subset of those differences. Extraction also used prefix-only catalogue recognition and could split a complete syringe-and-needle product at “and”.

`src/utils/generalProductMatching.ts` now supplies the shared clinical comparison and assignment engine. Exact and approved synonym groups receive priority. Structured ingredient, normalized mass/volume strength, concentration, dosage form, route, release and qualifier checks follow. A missing strength unit is accepted only against a unique explicit counterpart with matching numeric amount and form in a supported catalogue family. Fuzzy matching accepts only a uniquely supported minor error; two distinct known medicines and conflicting clinical specifications cannot be fuzzy-substituted. Competing candidates remain unresolved. Existing duplicate/split-line aggregation remains in the General Auditor.

The same engine supplies catalogue-backed CCA candidates before missing/extra classification and is used by raw comparisons, the server audit, confirmation recalculation and the frontend acceptance boundary. Source evidence retains its original text and structured clinical attributes; final products record their matching stage. Deterministic extraction and AI routing use the same catalogue-family recognition. Gemini continues to return bounded interpretations, not audit verdicts. No uncertain candidate becomes a verified product until the CCA explicitly confirms customer contact. Product confirmation preserves independent quantities, stock exemptions and approved limits. If a clinical distinction cannot safely be resolved, review is required rather than a guessed substitution.

For the reported order, Artesunate matches with a 15/10 quantity shortfall of 5. Ciprofloxacin injection versus a specified infusion remains a customer-verification candidate (15 requested, 10 supplied), not an automatic match or false extra. Selecting the customer-confirmed infusion immediately exposes its independent five-unit shortfall. No Gemini request is required for these cases.

`server/generalCentralProductMatching.test.ts` covers the reported cases and unrelated products, OCR, conflicting strengths/forms/routes/releases, competing candidates, duplicates, numbering, stock and quantity limits. It runs with `npm test`. `.github/workflows/ci.yml` runs the complete test suite, type check and build on Node 22 for pushes and pull requests. ### General Auditor document structure

The false heading warning originated in separate exact-label checks in extraction, interpretation-gap detection and product parsing. Variants such as `Products & Quantities:` could miss one check and reach the product-review workflow as unresolved text.

`src/utils/generalDocumentStructure.ts` now reads the complete message before product extraction. It records original text and line positions, classifies headings, fields, field values, product entries, notes and ambiguous content, and links multi-line values to their labels. Its position-preserving audit projection recognizes compositional labels, punctuation/capitalization variations, bounded OCR errors and short unfamiliar captions supported by following product entries. Inline product values are retained. Product counts after headings remain metadata rather than order quantities. Only product-entry lines reach the quantity parser; unknown product requests remain reviewable.

The shared projection runs through `generalOrderRelevantText`, raw product parsing and server extraction, so text, WhatsApp, screenshot/OCR, AI interpretation, confirmation recalculation and frontend reconciliation use the same structure rules. Gemini receives unresolved evidence after this preprocessing; its existing grounded-output validation remains in place. Stock section headings and explicit order amendments are preserved. Specific metadata labels retain their existing priority. Delivery area and district remain optional. Original audit inputs and confirmation fingerprints are not replaced by the projection.

### Product confirmation eligibility

Introductory statements and administrative/notification captions previously fell through to generic product review. In addition, there was no shared eligibility check separating identification, quantity and formulation review across old audit records, confirmation controls and server mutations.

The document parser now recognizes grammatical request introductions, administrative log captions, routine fulfilment notifications and bounded delivery instructions before product extraction. Inline medicines remain auditable; explicit amendments, named products and stock-section boundaries remain intact.

`src/utils/generalProductConfirmationPolicy.ts` is the common eligibility rule used by audit recalculation, confirmation saving and the interactive controls. Confirmation requires genuine source product evidence, an established catalogue identity, a valid requested quantity and a supported candidate with unresolved clinical attributes (including competing strength-unit candidates). Unknown identities and unclear quantities receive separate noninteractive review records. Final records include `reviewState`, and product comparisons include `productStatus`, independently of quantity findings. Generic older `warnings` messages remain available for API compatibility; the interface presents PRODUCT IDENTIFICATION REVIEW and QUANTITY REVIEW separately. Genuine clinical uncertainty displays DOSAGE / FORMULATION CONFIRMATION REQUIRED.

Old or AI-generated non-product verification records and their linked reviews are removed during summary rebuilding, rather than merely hidden. The server revalidates eligibility and the selected candidate before saving. Existing CCA identity, timestamps, input fingerprints, persistence and automatic recalculation remain in the existing workflow.
